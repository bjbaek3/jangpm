# 송무서면 생성기 — 설계문서

- 작성일: 2026-06-12
- 상태: 승인됨 (사용자 검토 완료 후 구현 계획으로 이행)
- 대상 환경: Claude Code (Windows 11), 단독 사용자(변호사 1인)

## 1. 목적과 범위

변호사 1인이 실제 민사사건에서 반복 사용하는 **실무용 서면 작성 도구**.
상담메모 등 텍스트 정리본을 입력받아, 법령(legalize-kr)·판례(precedent-kr)
원본 대조를 거친 **소장·준비서면 초안 DOCX**를 산출한다.

| 항목 | 결정 |
|---|---|
| 목적 | 실제 업무용 도구 (교육·데모 아님) |
| 사용자/환경 | 본인 단독, Claude Code CLI |
| 사건 범위 | 민사 전반 (청구 유형 중립) |
| 입력 | 상담메모·텍스트 정리본 (PDF/HWP는 변호사가 텍스트 변환 후 투입) |
| 산출 | DOCX (기존 docxtpl 템플릿 + render_서면.py 재사용) |
| 리서치 | 법령 + 판례 모두, 원본 전수 대조 검증 |
| 서면 종류 | 소장, 준비서면 2종 |

설계 원칙: **변호사는 문서가 아니라 사건 단위로 일한다.** 사건 폴더 하나가
사건 기록이자 작업 상태이며, 모든 단계 산출물이 파일로 남아 세션이 끊겨도
이어서 작업한다. 소장 단계에서 구축한 컨텍스트·법리가 준비서면에서 재입력
없이 재사용된다.

## 2. 아키텍처

모듈형 스킬 파이프라인. 사건 폴더(공유 상태) 위에 단계별 스킬 5종이 얹히고,
각 단계 사이에 변호사 검수 체크포인트가 있다. 인용 검증은 새 컨텍스트의
서브에이전트로 분리해 독립성을 확보한다.

```
워크스페이스 루트/
├─ CLAUDE.md                        ← 공유 규칙 진입점: 워크플로우, 인용규칙·스키마 참조, 안전수칙
├─ .claude/skills/
│   ├─ case-intake/SKILL.md        (사건구성)
│   ├─ legal-research/SKILL.md     (법리리서치)
│   ├─ draft-complaint/SKILL.md    (소장작성)
│   ├─ draft-brief/SKILL.md        (준비서면작성)
│   └─ verify-citations/SKILL.md   (인용검증)
├─ 규칙/
│   ├─ 인용규칙.md                   ← 조문·판례 인용 표기 + 출처 핀 규칙
│   └─ 사건컨텍스트.schema.json      ← canonical 스키마 정의 (JSON Schema)
├─ 문서 양식/                        (기존 자산 — 템플릿 2종, render_서면.py, make_templates.js)
├─ legalize-kr/                     (기존 — 법령 git 저장소, 3,054건)
├─ precedent-kr/                    (기존 — 판례 git 저장소)
└─ 사건/
    └─ {연도_의뢰인_사건요지}/        예: 2026_김민재_해고무효
        ├─ 입력/                     상담메모.md, 상대방_답변서.md … (변호사가 넣음)
        ├─ 사건컨텍스트.json          ← canonical 1벌, 단계가 갱신
        ├─ 리서치/쟁점별_법리.md      ← 원문 대조된 인용만 수록
        └─ 산출물/
            ├─ context_소장.json     (projection — 템플릿용 flat JSON)
            ├─ 소장_초안.docx
            ├─ 검증보고_소장.md
            └─ (준비서면 동일 세트: context_준비서면.json, 준비서면_초안.docx, 검증보고_준비서면.md)
```

## 3. 사건컨텍스트 스키마 (canonical)

민사 전반 범용, 청구 유형 중립. `규칙/사건컨텍스트.schema.json`으로 정의.

```jsonc
{
  "사건": { "사건명": "", "사건번호": null, "제출법원": "", "수임범위": "", "심급": "1심" },
  "당사자": {
    "원고": [ { "성명": "", "주민번호": "", "주소": "", "우편번호": "", "전화": "", "이메일": "" } ],
    "피고": [ { "명칭": "", "주소": "", "우편번호": "", "대표자": "" } ],
    "소송대리인": { "표시": "", "주소": "" }
  },
  "사실관계": [ { "일자": "2025.11.14.", "사실": "", "근거": "상담메모.md §2 / 갑2" } ],
  "쟁점": [ { "id": "쟁점1", "제목": "", "우리주장": "", "상대주장": null, "법리ref": "리서치#쟁점1" } ],
  "증거": [ { "표시": "갑1", "증거명": "", "입증취지": "" } ],
  "청구": [ { "유형": "확인|이행|형성", "청구취지문안": "", "금액": null, "산정내역": "" } ],
  "확인필요": [ "지연이자 이율", "관할 합의 여부" ]
}
```

핵심 설계 결정:

1. **사실관계 `근거` 필드 의무화** — 모든 사실 항목은 입력 파일의 출처
   (또는 증거 표시)를 가진다. 근거 없는 사실은 검증 단계에서 적발된다.
2. **`확인필요` 배열이 1급 시민** — 에이전트가 모르는 값(이율·관할 등)은
   추측하지 않고 여기 적재되며, 서면 말미 체크리스트로 자동 출력된다.
3. **당사자는 배열** — 다수당사자를 스키마 차원에서 선반영. 단 v1 렌더링은
   현 템플릿 한계로 원고·피고 각 1인 기준(§7 한계 참조).

## 4. 스킬 5종

### ① /case-intake {사건폴더} — 사건구성
- 입력: `입력/`의 상담메모·텍스트 전부
- 처리: `사건컨텍스트.json` 생성 또는 갱신(멱등). 필수 정보 누락 시
  그 자리에서 변호사에게 질문(AskUserQuestion), 미확보 항목은 `확인필요` 적재.
  쟁점 후보를 도출해 제시하되 **쟁점 확정은 변호사 승인 후 기록**.
  사실은 한 건도 생성하지 않음 — 모든 사실관계 항목에 `근거` 필수.
- 산출: `사건컨텍스트.json`

### ② /legal-research {사건폴더} — 법리리서치
- 입력: `사건컨텍스트.json`의 쟁점 목록
- 처리(쟁점별): legalize-kr grep으로 조문 탐색 → 해당 파일 **원문 발췌** →
  `git log`로 최신 개정일 확인(현행성) → precedent-kr grep으로 판례 탐색 →
  판시사항 원문 발췌 → 우리 사건 적용 논리 정리.
- 산출: `리서치/쟁점별_법리.md` (쟁점 → 조문 발췌+출처 핀 → 판례 발췌+출처 핀 → 적용 논리)
- **철칙: 원문을 직접 읽고 발췌하지 않은 조문·판례는 이 파일에 쓸 수 없다.**
  이후 작성 단계는 이 파일에 있는 인용만 사용 가능 — 환각 진입로를 이
  단계 하나로 단일화한다.

### ③ /draft-complaint {사건폴더} — 소장작성
- 입력: `사건컨텍스트.json` + `리서치/쟁점별_법리.md`
- 처리: `청구[]`에서 청구취지 도출(이행·확인·형성 유형별 정형 문안,
  소송비용 부담·가집행 선언 포함) → 청구원인 작성(당사자 지위 → 사실관계
  [타임라인 기반, 호증 표시] → 법적 주장[리서치 인용만] → 결론) →
  `context_소장.json` projection → **렌더 전 필수 키 대조** →
  `render_서면.py` 실행.
- 산출: `산출물/context_소장.json`, `산출물/소장_초안.docx`
  (말미에 `확인필요` 체크리스트 자동 첨부)

### ④ /draft-brief {사건폴더} — 준비서면작성
- 입력: 같은 `사건컨텍스트.json`(재사용) + `리서치/쟁점별_법리.md`(재사용) +
  `입력/상대방_답변서.md` 등 상대 서면 텍스트
- 처리: 상대 주장을 쟁점 단위로 분해 → `쟁점[].상대주장` 갱신 →
  주장별 대응 분류(**인정 / 부인 / 항변**) → 쟁점별 반박 본문
  (상대 주장 요지 → 반박 사실+증거 → 법리[리서치 재사용]) → 결론 →
  projection → 렌더.
- 리서치에 없는 새 쟁점 발견 시 **②로 돌아가도록 안내** — 임의로 법리를
  만들지 않는다.
- 산출: `산출물/context_준비서면.json`, `산출물/준비서면_초안.docx`

### ⑤ /verify-citations {사건폴더} {서면종류} — 인용검증
- **새 컨텍스트의 서브에이전트(Task)로 실행** — 작성자의 맥락·확신을
  물려받지 않은 독립 검사자.
- 처리: projection JSON에서 모든 법령·판례 인용 추출 → 건별 4단계 대조:
  - (a) 출처 핀의 파일 존재
  - (b) 조문/판시 내용이 서면의 주장과 실제 일치
  - (c) 법령 현행성 (git log 최신 개정 확인)
  - (d) 판례 사건번호·선고일자 정확성
  - 추가: 사실관계 중 `근거` 없는 문장 적발
- 산출: `산출물/검증보고_{서면}.md` — 인용별 ✅/⚠️/❌ 표.
  ❌가 하나라도 있으면 "검수 전 제출 금지" 상태 유지, 수정 후 재검증.

### 전형적 워크플로우

```
/case-intake → (검수) → /legal-research → (검수) → /draft-complaint → /verify-citations → 변호사 최종 검수
                                                        │
        상대 답변서 도착 시 같은 폴더에서 ──→ /draft-brief → /verify-citations   (재입력 0)
```

## 5. 인용규칙 (규칙/인용규칙.md)

- 본문 표기는 정식 인용례를 따른다:
  법령 `근로기준법 제27조`, 판례 `대법원 2010. 3. 25. 선고 2009다12345 판결`.
- 모든 인용 뒤에 **출처 핀** 병기:
  - 법령: `[출처: kr/근로기준법/법률.md | 현행확인 2026-06-12]`
  - 판례: `[출처: 민사/대법원/대법원_2010-03-25_2009다12345.md]`
- 출처 핀은 초안 DOCX까지 유지(검증 추적성), 최종 제출본에서 변호사가 제거.
- 리서치 파일에 발췌가 없는 법률 주장은 어느 서면에도 쓸 수 없다.

## 6. 렌더링 — 기존 자산 재사용과 변경점

- `문서 양식/`의 docxtpl 템플릿 2종, `render_서면.py`, `make_templates.js`를
  그대로 재사용. projection JSON의 키 구조는 기존
  `context_소장_예시.json` / `context_준비서면_예시.json`과 동일하게 유지.
- **유일한 변경**: 템플릿 푸터 워터마크 문구를
  `실습용 가상 사건 [초안] — 대외 제출 금지` →
  **`[초안] — 변호사 검수 전 제출 금지`** 로 교체
  (`make_templates.js` 수정 후 템플릿 재생성). 워터마크 자체는 미검수 초안의
  유출 사고를 막는 안전장치이므로 유지한다.
- 작성 스킬은 렌더 실행 전 projection JSON의 필수 키를 대조한다
  (렌더 실패의 주원인 차단).
- 셋업 요건: Python + `pip install docxtpl` (Windows 확인),
  템플릿 재생성 시 Node + `docx` 패키지.

## 7. 안전장치 총정리

| 리스크 | 장치 |
|---|---|
| 사실 환각 | 사실관계 `근거` 필드 의무 + 검증 단계에서 근거 없는 문장 적발 |
| 법리 환각 | 원문 발췌 없는 인용 금지 → 인용 진입로를 /legal-research 하나로 단일화 |
| 폐지·개정 조문 | git log 현행성 확인 + 출처 핀에 확인일 기록 |
| 가짜 판례 | 파일 존재 + 사건번호·선고일자·판시취지 4단계 대조 |
| 검증의 자기확신 | /verify-citations를 새 컨텍스트 서브에이전트로 분리 |
| 미검수 제출 사고 | 초안 워터마크 + 검증 ❌ 시 "제출 금지" 상태 명시 |
| 수치·이율 추측 | `확인필요` 적재 → 서면 말미 체크리스트 자동 출력 |

### 명시적 한계 (v1)

- 렌더링은 원고·피고 각 1인 기준 (스키마는 배열로 선반영, 템플릿 확장은 차후).
- 입력은 텍스트만. PDF·HWP·스캔본은 변호사가 텍스트로 변환해 `입력/`에 투입.
- precedent-kr 수록 범위(대법원 중심) 밖의 최신·하급심 판례는 찾지 못한다.
  리서치 산출물에 "저장소 수록 범위 내 검색" 문구를 항상 명시한다.
- 서면 종류는 소장·준비서면 2종. 추가 서면(답변서 등)은
  "템플릿 + 작성 스킬 1세트 추가"로 끝나도록 구조를 유지한다.

## 8. 테스트 계획

1. **E2E**: 기존 동해물류 가상 사건을
   `사건/예시_2026_김민재_해고무효/입력/상담메모.md`로 재구성 →
   5단계 파이프라인 전체 실행 → 소장·준비서면 DOCX + 검증보고 산출 확인.
2. **적대적 검증 테스트**: 폐지 조문, 존재하지 않는 판례번호, 근거 없는
   사실을 일부러 심은 초안에 /verify-citations를 실행해 ❌를 전부 잡는지 확인 —
   검증 게이트가 실제로 작동함을 증명하는 핵심 테스트.
3. **재실행 멱등성**: 리서치를 둔 채 /draft-complaint만 재실행해도 일관된 결과가
   나오는지, /case-intake 재실행이 기존 컨텍스트를 파괴하지 않는지 확인.
